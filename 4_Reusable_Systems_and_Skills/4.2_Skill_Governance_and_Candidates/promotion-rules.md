# Promotion Rules

Purpose: prevent VCOS from turning every exciting workflow into a bloated permanent skill.

## Promotion Path

1. **Experiment:** test the workflow in a real task.
2. **Pattern:** name the repeated behavior and capture rough steps.
3. **Skill Candidate:** define trigger, input packet, output packet, tools, failure mode, and approval gates.
4. **Validated Skill:** prove the workflow in 3 successful uses or across multiple client-like scenarios.
5. **Installed Capability:** add it to one department pack with least-privilege tool access.
6. **Marketplace Skill:** package only after client-safe assumptions, install notes, and examples are clean.

## Minimum Candidate Requirements

- named trigger phrase
- one owning department
- specific business outcome
- structured input packet
- structured output packet
- tools and credentials required
- approval gate
- QA or validation step
- failure mode and fallback
- proof lane: Amax, AgentOSync, barber demo, dealership, or other client-like test

## Promotion Tests

Promote only when most are true:

- used successfully at least 3 times
- reduces time, mistakes, cost, or context load
- can be tested in isolation
- has a clear owner
- works with short handoff packets
- does not require unnecessary secrets
- has a documented fallback
- can be taught to a new Mini Intern without the full original chat history

## Stop Conditions

Do not promote when:

- the workflow is a one-off experiment
- the output quality depends on hidden context only the human remembers
- the workflow needs broad credentials unrelated to its department
- the approval gate is unclear
- the failure mode is not detectable
- the workflow creates public/client-facing output without a QA path
